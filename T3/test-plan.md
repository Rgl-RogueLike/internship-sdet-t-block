# Задача T3. Составление тест-плана

## 1. Идентификатор плана тестирования

**TP-003**
План тестирования REST API `GET /products/{productId}/cost`.

---

## 2. Введение

Целью данного документа является описание подхода к тестированию REST API `GET /products/{productId}/cost`, предназначенного для расчета стоимости продукта в зависимости от количества экземпляров и начального индекса с нарастающим итогом.
Документ содержит анализ требований, стратегию тестирования, применяемые техники тест-дизайна и тест-кейсы.

---

## 3. Объект тестирования

Объектом тестирования является REST API 

`GET /products/{productId}/cost`

API предназначено для получения стоимости продукта.

Входные параметры:

- `productId`;
- `authToken`;
- `count`;
- `start`.

## 4. Анализ требований

### Входные параметры

| Параметр | Тип | Обязательный | Допустимые значения |
|-----------|-----|--------------|---------------------|
| `productId` | Path | Да | Идентификатор продукта |
| `authToken` | Query | Да | Строка из 16 буквенно-цифровых символов |
| `count` | Query | Да | 1,2,3,4,5 (и более, с учетом партионности) |
| `start` | Query | Да | 0,1,2,3,4 (и более, с учетом партионности) |

### Бизнес-логика расчета стоимости

| Количество приобретенных продуктов | 1 | 2 | 3 | 4 | 5 |
|-------------------------------------|---|---|---|---|---|
| Стоимость | 30 | 25 | 20 | 15 | 10 |

- Вычисление выполняется нарастающим итогом.
- Приобретение возможно только партиями по 5 экземпляров. При запросе `count > 5` расчет идет по кругу таблицы (6-й экземпляр стоит как 1-й, то есть 30, и т.д.). 

### Возможные ответы сервиса

| HTTP-код | Описание |
|-----------|----------|
| 200 | Стоимость продукта успешно рассчитана |
| 401 | Невалидный или отсутствующий `authToken` |
| 404 | Продукт не найден |
| 500 | Внутренняя ошибка сервера, в том числе при невалидных параметрах `count` и `start`, так как иные коды не предусмотрены | 

## 5. Стратегия тестирования

### Общий подход

Тестирование выполняется методом черного ящика на основе требований к REST API без анализа внутренней реализации сервиса.

Основное внимание уделяется:

- проверке корретной обработки входных параметров;
- проверке математической логики расчета стоимости (нарастающий итог и партийность);
- проверке обработки позитивных и негативных сценариев;
- проверке структуры и содержимого ответов сервиса;
- проверке обработки ошибок.

### Уровни тестирования

В рамках данного тест-плана выполняется функциональное тестирование REST API на уровне системного тестирования.

## 6. Критерии начала тестирования

Тестирование может быть начато при выполнении следующих условий:

- требования к API согласованы;
- REST API доступно для тестирования;
- известны значения тестовых параметров (`productId`, `authToken`);
- подготовлено тестовое окружение.

## 7. Критерии завершения тестирования

Тестирование считается завершенным при выполнении следующих условий:

- выполнены все предусмотренные тест-кейсы;
- проверены позитивные и негативные сценарии;
- выявленые дефекты зарегистрированы;
- результаты тестирования оформлены. 

## 8. Критерии приостановки и возобновления тестирования

### Приостановка тестирования 

Тестирование приостанавливается в следующих случаях:

- сервис недоступен;
- отсутствует тестовое окружение;
- невозможно выполнить тестовые сценарии из-за критического дефекта.

### Возобновление тестирования

Тестирование продолжается после устранения причин приостановки и восстановления работоспособности тестового окружения.

## 13. План тестирования

В рамках тестирования необходимо проверить следующие аспекты работы REST API:

1. **Проверка авторизации**
    - запрос с валидным `authToken`;
    - запрос с отсутствующим `authToken`;
    - запрос с невалидным `authToken`.
2. **Проверка параметра `productId`**
    - расчет стоимости существующего продукта;
    - запрос несуществующего продукта.
3. **Проверка бизнес-логики расчета стоимости (параметры `count` и `start`)**
    - расчет полной первой партии (`count = 5`, `start = 0`);
    - расчет неполной партии с начала (`count = 2`, `start = 0`);
    - расчет со смещением `start` (`count = 2`, `start = 2`);
    - расчет 1 товара при максимальном `start` по таблице (`count = 1`, `start = 4`);
    - проверка перехода на новую партию при `count > 5` (`count = 6`, `start = 0`);
    - проверка партионности со смещением `start` (`count = 7`, `start = 4`).
4. **Проверка невалидных значений `count` и `start`**
    - передача `count = 0`;
    - передача отрицательных значений `count` и `start`;  
    - передача строковых значений в числовые параметры.
5. **Проверка успешного ответа**
    - HTTP-код `200`;
    - соответствие структуры JSON требованиям;
    - корректность математического значения `cost`.
6. **Проверка обработки ошибок**
    - возврат HTTP-кода `401` при отсутствии или неверном токене;
    - возврат HTTP-кода `404` при отсутствии продукта;
    - возврат HTTP-кода `500` при ошибке обработки запроса с телом в формате JSON, содержащим поле `errorMessage`.

## 14. Применяемые техники тест-дизайна

### 14.1 Классы эквивалентности

Для сокращения количества тестов входные данные были разделены на классы эквивалентности. Из каждого выбрано по одному или нескольким представителям.

| Параметр | Валидные классы | Невалидные классы | Тест-кейсы |
|-----------|-----------------|-------------------|------------|
| `authToken` | Строка из 16 буквенно-цифровых символов | отсутствует; длина != 16; невалидные символы | TC-001–TC-005, TC-018 |
| `productId` | Существующий идентификатор | Несуществующий идентификатор | TC-001, TC-006, TC-017 |
| `count` | 1-5; > 5 (с учетом партий) | 0; отрицательные; строки | TC-007–TC-016, TC-011–TC-014 |
| `start` | 0-4; > 4 (с учетом партий) | отрицательные; строки | TC-007–TC-016, TC-13 |

### 14.2 Анализ граничных значений

Для параметров `count`, `start` и `authToken` применен анализ граничных значений.

| Параметр | Значение | Ожидаемый результат | Тест-кейс |
|-----------|----------|---------------------|-----------|
| | 15 символов | Ошибка авторизации (`401`) | TC-004 |
| | 16 символов | Успешная авторизация | TC-001 |
| | 17 символов | Ошибка авторизации (`401`) | TC-005 |
| | 0 | Ошибка (`500`) | TC-011 |
| | 1 (минимальное значение) | Успешный расчет (`200`) | TC-001 |
| | 6 (переходное значение) | Успешный расчет (`200`) | TC-010 |
| | 0 (минимальное значение) | Успешный расчет (`200`) | TC-001 |
| | 4 (максимальное по таблице) | Успешный расчет (`200`) | TC-008 |

### 14.3 Негативное тестирование

| Проверяемая ситуация | Тест-кейс |
|-----------------------|-----------|
| Отсутствует `authToken` | TC-002 |
| Невалидный `authToken` | TC-003 |
| Несуществующий `productId` | TC-006 |
| Невалидное значение `count = 0` | TC-011 |
| Отрицательное значение `count` | TC-012 |
| Отрицательное значение `start` | TC-013 |
| Строковое значение `count` | TC-014 |

### 14.4 Попарное тестирование

Для проверки совместной работы параметров `count` и `start` (включая выход за пределы базовой таблицы) использовано попарное тестирование.

Проверяются комбинации параметров:

| `productId` | `authToken` | `count` | `start` | Тест-кейс |
|--------------|-------------|---------|---------|-----------|
| Valid | Valid | 5 | 4 | TC-015 |
| Valid | Valid | 6 | 5 | TC-016 |
| Invalid | Valid | 1 | 0 | TC-017 |
| Valid | Invalid | 6 | 0 | TC-018 |

| **Шаги** | 1. Отправить GET-запрос с валидными `authToken`, `count = 6`, `start = 5`. |
| **Ожидаемый результат** | Получен HTTP-код `200`. Стоимость: 30+25+20+15+10 (за 6-10) + 30 (за 11-й) = `{"cost": 130}`. |  

#### TC-017. Комбинация `productId = Invalid`, `count = 1`, `start = 0` (Invalid, Valid, Valid)

### 15.6 Проверка успешного ответа

Покрывается тест-кейсами TC-001, TC-007, TC-009 и др.

- HTTP-код `200`;
- соответствие структуры JSON требованиям `{"cost": <число>}`.

### 15.7 Проверка обработки ошибок

Раздел покрывается тест-кейсами:

- TC-002, TC-003, TC-004, TC-005, TC-018 - проверка HTTP-кода `401`;
- TC-006, TC-017 – проверка HTTP-кода `404`;
- TC-011, TC-012, TC-013, TC-014 – проверка HTTP-кода `500` и структуры сообщения об ошибке `{"errorMessage": "..."}`.
