# Задача T1. Написание тест-кейсов

## 1. Идентификатор плана тестирования

**TP-001**
План тестирования REST API `GET /products/{productId}/status`.

---

## 2. Введение

Целью данного документа является описание подхода к тестированию REST API `GET /products/{productId}/status`, предназначенного для получения статуса продукта по его идентификатору.

Документ содержит анализ требований, стратегию тестирования, применяемые техники тест-дизайна и тест-кейсы.

---

## 3. Объект тестирования

Объектом тестирования является REST API:

`GET /products/{productId}/status`

API предназначено для получения статуса продукта по его идентификатору.

Входные параметры:

- `productId`;
- `authToken`;
- `recalculate`;
- `owner`;
- `region`.

## 4. Анализ требований

### Входные параметры

| Параметр | Тип | Обязательный | Допустимые значения |
|-----------|-----|--------------|---------------------|
| productId | Path | Да | Идентификатор продукта |
| authToken | Query | Да | Строка из 16 буквенно-цифровых символов |
| recalculate | Query | Нет | true, false, null |
| owner | Query | Нет | Создатель, Пользователь, null |
| region | Query | Нет | Северо-Запад, Сибирь, Поволжье |

### Возможные ответы сервиса

| HTTP-код | Описание |
|-----------|----------|
| 200 | Статус продукта успешно получен |
| 401 | Неверный или отсутствующий authToken |
| 404 | Продукт не найден |
| 500 | Внутренняя ошибка сервера |

## 5. Стратегия тестирования

### Общий подход

Тестирование выполняется методом черного ящика на основе требований к REST API без анализа внутренней реализации сервиса.

Основное внимание уделяется:

- проверке корректной обработки входных параметров;
- проверке обязательных и необязательных параметров;
- проверке обработки позитивных и негативных сценариев;
- проверке структуры и содержимого ответов сервиса;
- проверке обработки ошибок.

### Уровни тестирования

В рамках данного тест-плана выполняется функциональное тестирование REST API на уровне системного тестирования.

## 6. Критерии начала тестирования

Тестирование может быть начато при выполнении следующих условий:

- требования к API согласованы;
- REST API доступно для тестирования;
- известны значения тестовых параметров (`productId`, `authToken`);
- подготовлено тестовое окружение.

## 7. Критерии завершения тестирования

Тестирование считается завершенным при выполнении следующих условий:

- выполнены все предусмотренные тест-кейсы;
- проверены позитивные и негативные сценарии;
- выявленные дефекты зарегистрированы;
- результаты тестирования оформлены.

## 8. Критерии приостановки и возобновления тестирования

### Приостановка тестирования 

Тестирование приостанавливается в следующих случаях:

- сервис недоступен;
- отсутствует тестовое окружение;
- невозможно выполнить тестовые сценарии из-за критического дефекта.

### Возобновление тестирования

Тестирование продолжается после устранения причин приостановки и восстановления работоспособности тестового окружения.

## 9. Среда тестирования

## 10. Результаты тестирования 

Результаты выполнения тест-кейсов фиксируются в тестовой документации.

При обнаружении несоответствий создаются Bug Report с описанием дефекта, шагами воспроизведения, ожидаемым и фактическим результатом.

## 11. План тестирования

В рамках тестирования необходимо проверить следующие аспекты работы REST API:

1. **Проверка авторизации**
    - запрос с валидным `authToken`;
    - запрос с отсутствующим `authToken`;
    - запрос с невалидным `authToken`.

2. **Проверка параметра `productId`**
    - получение статуса существующего продукта;
    - запрос несуществующего продукта.

3. **Проверка параметра `recalculate`**
    - передача допустимых значений (`true`, `false`, `null`);
    - отсутствие параметра;
    - передача невалидного значения.

4. **Проверка параметра `owner`**
    - передача допустимых значений (`Создатель`, `Пользователь`, `null`);
    - отсутствие параметра;
    - передача невалидного параметра

5. **Проверка параметра `region`**
    - передача допустимых значений (`Северо-Запад`,`Сибирь`, `Поволжье`);
    - отсутствие параметра;
    - передача невалидного значения.

6. **Проверка успешного ответа**
    - HTTP-код `200`;
    - соответствие структуры JSON требованиям;
    - корректность значения `productStatus`.

7. **Проверка обработки ошибок**
    - возврат HTTP-кода `401` при отсутствии или неверном токене;
    - возврат HTTP-кода `404` при отсутствии продукта;
    - возврат HTTP-кода `500` при ошибке обработки запроса с телом ответа в формате JSON, содержащим поле `errorMessage`, согласно требованиям.

## 12. Применяемые техники тест-дизайна

### 12.1 Классы эквивалентности

Для сокращения количества тестов входные данные были разделены на классы эквивалентности. Из каждого класса выбрано по одному или нескольким представителям.

| Параметр | Валидные классы | Невалидные классы | Тест-кейсы |
|-----------|-----------------|-------------------|------------|
| `authToken` | Строка из 16 буквенно-цифровых символов | отсутствует; длина != 16; невалидный | TC-001 – TC-005 |
| `productId` | Существующий идентификатор | Несуществующий идентификатор | TC-001, TC-006 |
| `recalculate` | `true`, `false`, `null`, отсутствует | Любое другое значение | TC-007 – TC-011 |
| `owner` | `Создатель`, `Пользователь`, `null`, отсутствует | Любое другое значение | TC-012 – TC-016|
| `region` | `Северо-Запад`, `Сибирь`, `Поволжье`, отсутствует | Любое другое значение | TC-017 – TC-021 |

### 12.2 Анализ граничных значений

Для параметра `authToken` применен анализ граничных значений по длине строки.

| Длина `authToken` | Ожидаемый результат | Тест-кейс |
|--------------------|---------------------|-----------|
| 15 символов | Ошибка авторизации (`401`) | TC-004 |
| 16 символов | Успешная авторизация | TC-001 |
| 17 символов | Ошибка авторизации (`401`) | TC-005 |

### 12.3 Негативное тестирование

| Проверяемая ситуация | Тест-кейс |
|-----------------------|-----------|
| Отсутствует `authToken` | TC-002 |
| Невалидный `authToken` | TC-003 |
| Несуществующий `productId` | TC-006 |
| Невалидное значение `recalculate` | TC-009 |
| Невалидное значение `owner` | TC-014 |
| Невалидное значение `region` | TC-019 |

### 12.4 Попарное тестирование

Для проверки совместной работы необязательных параметров использовано попарное тестирование, позволяющее сократить количество комбинаций без существенного снижения покрытия.

Проверяются комбинации параметров:

| `recalculate` | `owner` | `region` | Тест-кейс |
|-----------------|---------|----------|-----------|
| true | Создатель | Северо-Запад | TC-024 |
| false | Пользователь | Сибирь | TC-025 |
| null | null | Поволжье | TC-026 |
| true | Пользователь | Поволжье | TC-027 |
